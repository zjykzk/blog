# 产品经理的核心职能

产品经理的核心职能，是在资源有限、信息不完整的情况下，判断应该为谁解决什么问题，并推动团队用尽可能低的成本验证这项判断。

## What It Is

产品经理处理的不是单个功能，而是产品方向上的不确定性与协作问题。其核心产出不是需求文档或原型，而是更可靠的选择：现在服务谁、解决什么、为什么值得做、哪些不做，以及什么证据会改变当前决定。^[inferred]

产品决策通常同时面对四类不确定性：

| 不确定性 | 核心问题 |
|---|---|
| 用户与问题 | 谁在什么场景中受阻，真实目标和问题强度是什么？ |
| 价值与商业 | 问题是否值得解决，用户是否愿意采用，组织能否获得可持续回报？ |
| 方案与可行性 | 什么机制能产生目标结果，技术、成本和风险边界是否允许？ |
| 结果与学习 | 上线后的行为是否证明原判断成立，应该继续、调整还是停止？ |

## How It Works

产品经理通过一个持续循环缩小这些不确定性：

```text
发现问题
  -> 选择值得解决的问题
  -> 定义目标、边界与成功标准
  -> 组织设计、研发、运营和商业协作
  -> 从真实使用中获得证据
  -> 修正问题、方案或优先级
```

### 发现问题

用户表达的常常是期望方案，而不是稳定的问题定义。[[wiki/topics/Problem Framing|问题定义]]先明确目标用户、发生场景、预期结果、现实阻碍与问题代价，防止团队把“增加一个功能”误当作问题本身。

### 选择与取舍

用户需求、商业目标、技术约束和管理诉求不会天然一致。产品经理需要明确优先级、机会成本与非目标，把有限资源集中到更值得验证的问题上。上游决定还会约束后续方案，因此高影响问题应先于实现细节被稳定下来；这与[[wiki/concepts/Dependency-Ordered Decision Making|依赖驱动的逐项决策]]相通。^[inferred]

### 定义共同结果

“交付某项功能”描述产出，不等于用户或商业结果。产品经理需要把目标、边界、验收条件和取舍理由转成跨职能团队可以共同使用的判断依据。[[wiki/topics/User Stories|用户故事]]是表达“谁、想完成什么、为什么”的工具之一，但不是产品工作的终点。

### 验证并修正

上线把内部判断暴露给真实世界。行为数据、访谈、实验、销售反馈与运营结果进入下一轮决策，形成[[wiki/concepts/Feedback Loops|反馈回路]]。反馈的作用不是证明原方案正确，而是尽早暴露错误假设并改变后续投入。^[inferred]

## Structural Model

产品经理工作的真实约束是时间、资金、研发能力和组织注意力都有限，而用户信号又分散、冲突且带有解释偏差。

系统如果奖励功能数量、按期上线和汇报完整度，产品团队就容易高效制造并交付错误方案。只有让真实用户结果和商业结果回到优先级与资源配置中，反馈才会纠正方向。错误方向持续得越久，代码、流程、承诺与组织利益就越容易围绕它固化，转向成本也越高。^[inferred]

因此，这项工作的结构可以压缩为：

> 在有限资源和多方诉求的约束下，产品经理把分散信号转化为可执行取舍，并让真实结果持续校正下一轮决策，从而降低团队高效制造错误产品的概率。

## Role Boundary

产品经理不是单纯的需求收集者、文档作者或排期管理员。这些活动只有在改善问题判断、资源取舍、共同理解或验证速度时才产生产品价值。

产品经理也不必亲自完成研究、设计、开发、销售和运营，更不意味着对所有参与者拥有行政权。其责任是保持产品决策闭环完整，让关键问题有人判断、取舍有明确依据、结果能够回流。^[inferred]

产品管理首先是一种组织功能，其次才是一个职位。创业团队可能由创始人承担，成熟团队也可能由产品、设计、工程和业务共同承担；没有专职产品经理，不等于这项功能可以消失。^[inferred]

## When to Use

这个模型适合用来：

- 判断产品经理应负责方向决策，还是正在退化为需求传递与项目跟踪；
- 设计产品流程时，检查问题发现、优先级、协作和验证是否形成闭环；
- 评价产品工作时，从文档和功能数量转向决策质量、共同理解与反馈速度；
- 划分岗位边界时，区分产品管理功能与特定职位名称。

## Quality Check

一项产品管理工作是否有效，可以检查：

- 团队是否清楚正在为谁解决什么问题；
- 资源是否投入到当前最值得验证的问题；
- 目标、非目标、边界和成功标准是否形成共同理解；
- 上线后的证据是否真正改变后续选择；
- 当证据否定原判断时，团队是否能够停止或转向。
