# Classification Procedure

分类不是把东西分堆，而是把一组混乱对象，按某个问题目标，切成若干互斥、可解释、可使用的类别。

它的核心问题不是“有哪些类别”，而是：**我为什么要分类，分类之后要改变什么理解、判断或行动。**

## Core Formula

一个可用分类至少包含五个要素：

```text
分类 = 对象 + 目标 + 维度 + 边界 + 用途
```

- **对象**：现在要分的到底是什么，例如人、需求、bug、风险、知识、系统问题或方法论。
- **目标**：为什么要分，是为了理解、决策、排优先级、管理、迁移知识、找根因，还是形成行动方案。
- **维度**：按什么标准分，例如来源、功能、阶段、层级、责任主体、因果位置、抽象程度、稳定性或行动策略。
- **边界**：每一类和另一类的判别标准是什么；如果一个对象同时像两类，按什么主规则处理。
- **用途**：分完之后能做什么；如果所有类别后续动作都一样，这个分类通常只是命名游戏。

## Principle: Classify by the Problem, Not by Surface Features

同一批对象会因为目标不同而需要不同切法。

需求如果为了分派实现责任，可以按页面、接口、数据、权限分类；如果为了排优先级，就可能要按核心业务闭环、合规风险、体验改善和技术债分类；如果为了减少返工，则应按问题定义不清、业务规则复杂、跨系统依赖强和展示为主等差异来分类。

因此分类前应先问：**我分类之后，是为了看见什么差异？**

## 从目的反推维度

目的不会直接给出维度。必须先把目的翻译成一个待做决策，再从会改变决策的行动差异反推维度：

```text
目的 → 待做决策 → 不同处理 → 处理差异的原因 → 候选维度
```

### 1. 把目的改写为动作问题

“提高效率”“管理风险”“整理知识”都还不是足够具体的目的。应改写为：

- 我要决定先处理哪一个？
- 我要决定交给谁？
- 我要决定使用哪种方案？
- 我要决定立即处理、继续观察还是放弃？

如果无法说出分类后要改变什么动作，目的还没有被操作化。

### 2. 比较应该不同处理的样本

从实际案例中寻找三类样本对：

- 看起来相似，但应该不同处理；
- 看起来不同，但应该相同处理；
- 明显应该进入不同处理路径。

逐对追问：“为什么 A 和 B 不能用同一种方式处理？”答案通常会暴露紧迫性、影响范围、责任边界、产生机制、可恢复性等候选维度。

### 3. 把原因改写成可观察变量

“重要”“复杂”“特殊”只是模糊判断，不是可执行维度。需要继续拆成可观察变量，例如把“重要”拆成影响用户数、单次损失、是否阻塞核心流程、是否涉及合规、是否继续扩散。

可用维度必须说明观察对象、可能取值、判别方法和判断责任人。^[inferred]

### 4. 用反事实筛选候选维度

保持其他条件不变，只改变候选维度，检查分类结果或处理方式是否随之改变：

> 如果只改变这个差异，行动仍然不变，它就不是当前目的下的强维度。

这个测试把“相关特征”与“决策相关特征”分开。它检验的是维度对当前分类目的的操作价值，不足以单独证明因果关系。^[inferred]

### 5. 区分维度、指标和类别

- **维度**是变化轴，例如风险、紧迫性、责任主体；
- **指标**是测量维度的信号，例如损失金额、影响人数、恢复时间；
- **类别**是沿维度划出的区间或状态，例如低风险、中风险、高风险。

多个指标可以共同构成一个维度；多个独立维度则应使用主分类加标签、二维矩阵或综合评分，不能把不同维度的取值混成同一层类别。

## 从样本系统地产生并比较候选维度

### 1. 建立样本卡片

为每个样本记录同一组字段，使差异可比较：

| 字段 | 要回答的问题 |
|---|---|
| 情境 | 在什么条件下出现？ |
| 结果 | 产生了什么后果？ |
| 当前处理 | 实际采用了什么动作？ |
| 理想处理 | 按分类目的应该怎样处理？ |
| 处理理由 | 为什么这样处理？ |
| 证据 | 哪些事实支持这个理由？ |

字段不是预设维度，而是为维度发现提供共同观察面。缺少共同字段时，样本差异很容易被叙述方式而非对象结构主导。^[inferred]

### 2. 构造对比样本对

系统选择三类配对：

- **同表象、异处理**：寻找被表面相似遮住的关键差异；
- **异表象、同处理**：寻找跨表象保持不变的共同机制；
- **边界对**：寻找只改变一个条件就会改变处理的邻近样本。

对每一对填写：“哪项差异解释了处理分叉？”把答案汇总、去重，形成初始候选维度池。

### 3. 用观察镜头补全候选池

样本比较容易受现有案例限制，可再用八类镜头主动提问：

1. **属性**：对象有什么稳定特征；
2. **功能**：对象在整体中起什么作用；
3. **机制**：对象为什么产生当前结果；
4. **阶段**：对象处于哪个生命周期位置；
5. **主体**：谁发起、控制、承受或负责；
6. **状态**：对象当前允许什么变化；
7. **关系与情境**：它与什么连接，在何种条件下成立；
8. **决策约束**：成本、风险、可逆性、紧迫性和可控性如何。

这些镜头只负责生成候选，不能因为“维度常见”就直接采用。

### 4. 把候选写成维度卡

每个候选维度统一写成：

```text
维度名称：
它测量的差异：
可能取值：
观察指标：
边界判据：
会改变的决策或动作：
不适用条件：
```

如果无法写清“会改变的动作”，它更可能是描述性标签；如果无法写清观察指标和边界判据，它还只是模糊概念。

### 5. 用评分矩阵比较

可对候选维度按 `0–2` 分评分：

| 标准 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 行动区分度 | 不改变动作 | 偶尔改变 | 稳定改变 |
| 类内一致性 | 同类处理差异大 | 部分一致 | 处理高度一致 |
| 类间分离度 | 不同类仍同处理 | 部分分离 | 明确分离 |
| 可观察性 | 主要靠感觉 | 可间接判断 | 有直接证据 |
| 覆盖度 | 只解释少数样本 | 覆盖主要样本 | 含边界样本仍有效 |
| 稳定性 | 换情境即失效 | 特定范围稳定 | 在目标范围内稳定 |
| 独立增量 | 与已有维度重复 | 部分新增 | 提供独立信息 |
| 使用成本 | 高于收益 | 成本可接受 | 低成本高收益 |

总分只用于初筛，不能替代判断。与目标直接相关的硬约束可以设置为门槛，例如安全分类要求证据可观察性不得为零。^[inferred]

### 6. 用留出样本验证

不要只在产生维度的样本上验证。保留一组未参与设计的样本，检查：

- 新样本能否稳定归类；
- 同类是否导出相近处理；
- 不同类是否真的产生行动差异；
- 边界案例是否暴露缺失维度；
- “其他 / 未知”是否快速膨胀。

如果训练样本表现很好、留出样本频繁失效，这个维度更像对现有案例的过拟合。^[inferred]

### 7. 选择合适的表达结构

- 一个维度足以决定动作：使用单维分类；
- 一个主维度决定主路径，其他维度只补信息：主分类加标签；
- 两个维度交互决定动作：二维矩阵；
- 多个连续指标共同决定强度：综合评分，但保留指标明细；
- 关键差异来自生成过程：优先使用机制分类，而不只是表面属性。

## 建立有边界的对象全集

分类前无法证明开放世界中的对象绝对齐全。可操作目标是建立一个**有边界、可审计、可继续发现遗漏的对象池**：

```text
对象覆盖
= 范围契约 + 多路径枚举 + 反例搜索 + 未知入口 + 停止条件
```

### 区分三种全面性

- **对象全面**：该进入判断范围的实例或类型是否被发现；
- **类别全面**：已发现对象是否都能进入某个类别；
- **视角全面**：是否覆盖所有会改变结论的重要观察角度。

MECE 主要检查第二项。一个分类可以完整覆盖一个定义过窄的对象池，因此“不重不漏”不能单独证明对象全面。^[inferred]

### 1. 写范围契约

对象池至少需要五项边界：

- **对象单位**：一条需求、一次故障、一个用户，还是一种机制；
- **空间边界**：哪些系统、组织、地区或上下游在范围内；
- **时间边界**：观察哪个时期；
- **状态边界**：只看已发生、已记录、仍有效，还是也包含潜在对象；
- **纳入与排除规则**：哪些对象进入，重复、派生或无证据对象如何处理。

没有范围契约，“是否全面”就没有可检验的参照物。这与 [[wiki/topics/Problem Framing]] 先锁定问题边界的要求一致。

### 2. 从独立路径枚举

不能只依赖一张现成清单。应从多条相互独立的路径建立候选对象：

- **结构**：系统、模块、角色、组成部分；
- **流程**：产生、进入、处理、验证、交付、运行、反馈；
- **主体**：用户、执行者、审批者、受影响者、外部合作方；
- **状态**：正常、异常、未知、失败、恢复、终止；
- **来源**：数据库、日志、工单、监控、访谈、文档、现场观察；
- **边界与例外**：跨域、混合、罕见、沉默、被绕过或无法归类的对象。

多条路径反复发现同类对象，说明覆盖趋于收敛；新路径仍持续发现新类型，说明对象池尚未饱和。^[inferred]

### 3. 用父子覆盖与反例检查

[[wiki/concepts/Logic Tree and Pyramid Principle]] 要求同层子节点共同解释或覆盖父节点。对每个父节点检查：

1. 同层是否使用同一切分维度；
2. 分支是否重复或遗漏；
3. 子节点合起来是否覆盖父节点；
4. 是否存在无法进入任何分支的实例；
5. 删除某个分支后，父节点是否仍被完整解释。

同时主动搜索边界案例、反例、极端案例、失败案例、跨域案例、沉默案例和历史案例。树内部满足 MECE，只说明结构自洽；外部反例才能暴露父边界本身是否过窄。^[inferred]

### 4. 保留未知入口

`其他 / 未知 / 待判断` 是遗漏传感器，不是永久垃圾桶。应记录其中对象的来源和增长速度：

- 持续增长，说明维度、边界或数据入口需要重构；
- 长期为空，不足以证明全面，也可能意味着信息来源过于单一；
- 某类未知反复出现，应升级为正式类别或新的采集渠道。

### 5. 用经验饱和停止搜索

记录每增加一个独立来源所发现的新对象数和新类型数。当连续多个来源不再产生新类型，继续搜索的边际收益趋低，可以暂时停止。

这不是逻辑上的绝对完备，而是当前范围、证据来源和成本约束下的**经验饱和**。更稳的完成标准是：边界和停止条件明确，未覆盖区域被记录，新对象出现时能够触发分类修订。^[inferred]

## Common Dimensions

### 1. 层级分类

层级分类适合理解复杂系统，避免把表现层、机制层、结构层和治理层混在一起。

例如系统问题可以分为页面报错、接口失败等表现层；状态流转、并发控制、缓存策略等机制层；模块边界、数据模型、服务依赖等结构层；需求变更、发布流程、责任机制、监控反馈等治理层。

### 2. 因果位置分类

因果位置分类适合根因分析。它把触发因素、近因、中层机制、深层设计原因和组织原因区分开，防止只修这次爆出来的症状。

### 3. 生命周期分类

生命周期分类适合分析流程、项目、需求和知识生产。它按产生、澄清、设计、实现、验证、上线、反馈等阶段定位问题发生的位置。

### 4. 责任主体分类

责任主体分类适合协作和治理问题。它把问题映射到产品定义、架构设计、开发实现、测试覆盖、运维监控、业务使用或管理决策等可改变位置。

### 5. 功能分类

功能分类适合拆系统、工具和方法论。它关注每个部分在整体里起什么作用，例如定义问题、收集信息、建模分析、判断优先级、形成行动和反馈修正。

### 6. 稳定性分类

稳定性分类适合架构和知识管理。稳定概念、场景经验、操作技巧和临时信息应被不同方式保存与复用。

### 7. 抽象层次分类

抽象层次分类适合学习和表达。它把“怎么用”“有什么规则”“内部模型如何运转”“为什么这样设计”“这个思想可迁移到哪里”分开。

### 8. 行动策略分类

行动策略分类适合决策。问题可以被分成立即修复、暂时规避、继续观察、建立监控、重构治理或放弃处理等类别。

## Operating Flow

### 1. 写清对象

先写一句：我现在要分类的是 `X`。

如果对象没有被锁定，分类会滑向泛泛的目录整理。

### 2. 写清目的

再写一句：我分类是为了 `Y`。

目的决定主维度。理解、决策、责任分派、根因分析和行动优先级通常需要不同切法。

### 3. 建立对象池并列原始样本

先写清对象单位、空间、时间、状态及纳入/排除边界，再从结构、流程、主体、状态、证据来源和例外路径独立枚举。不要一开始就造分类；先列 10–20 个具体案例，记录它们何时发生、由谁提出、为何出现、影响什么、是否可预防。

分类应从样本中长出来，而不是先拍脑袋定格子。对象池还应保留未知入口，并用新来源能否继续产生新类型判断经验饱和。^[inferred]

### 4. 找候选维度

先写出分类要支持的决策，再比较应该采用不同处理方式的样本，追问处理差异由什么造成。把答案改写成可以观察、取值和判别的变量。

### 5. 选择主维度

对候选维度做反事实测试：保持其他条件不变，只改变该维度，判断或行动是否会改变。优先选择行动区分度高、解释力强、可观察、覆盖面广且判断成本低的维度。^[inferred]

一次先选最服务目标的一个主维度。多个维度可以作为标签、矩阵、综合评分或后续细分，但不要把不同维度混成同一层级。

### 6. 校准抽象层级

在同一维度上，比较当前分类与相邻的上位、下位层级：向上合并是否突然丢掉大量可预测属性或处理方式？向下细分是否只增加名称与判断成本，却很少改变行动？

[[wiki/concepts/Basic-Level Categorization]]把这个问题表述为认知经济与信息量的折中。它不是要求永远选“中间层”，而是要求为当前知识共同体与任务找到收益跃迁最大的层级。^[inferred]

### 7. 写判别标准和处理策略

每一类至少要写清两件事：

- **判别标准**：什么情况下算这一类，边界情况如何处理。
- **处理策略**：这一类对应什么不同动作、资源、优先级或检查方式。

分类只有走到处理策略，才从“看起来有条理”变成“能改变下一次行为”。

## Quality Checks

一个分类做完后，应检查：

1. 对象单位、时间、空间、状态和纳入/排除边界是否明确。
2. 是否从结构、流程、主体、状态、来源和例外等独立路径枚举对象。
3. 类别是否尽量不重叠、不遗漏；如果天然重叠，应改成标签体系而不是强行唯一归类。
4. 类名背后是否有清楚判别标准，而不只是好听名词。
5. 不同类别是否对应不同后续动作。
6. 同一层级是否只使用一个主维度，避免把业务模块、技术组件、优先级和问题性质混在一起。
7. 粒度是否合适：太细会变成命名个案，太粗会失去解释力。
8. 是否保留未知入口，并记录尚未覆盖的区域与经验饱和证据。
9. 分类是否允许随理解、样本和目标变化而演化。

## Common Failure Modes

- **用名词代替标准**：只说“技术类、业务类、管理类”，却没有说明判别规则。
- **混合维度**：把高优先级、页面需求、后端需求、合规需求放在同一层。
- **分类太细**：每个类只有一个样本，无法形成可复用处理方式。
- **分类太粗**：所有问题都叫“沟通问题”，没有解释力。
- **没有后续动作**：分类完只是整理得好看，但无法指导下一步。

## Descriptive and Generative Classification

分类可以分成两类：

- **描述型分类**：回答这些东西表面上有什么不同，例如前端问题、后端问题、数据问题。
- **生成型分类**：回答这些东西为什么会变成这样，例如边界定义不足、状态模型不完整、反馈链路过长、责任接口不清或历史债务累积。

更有穿透力的分类通常是生成型分类。它不是按现象分，而是按产生机制分。^[inferred]

## One-Sentence Compression

> 好分类不是把对象放进漂亮格子，而是按当前问题目标切出能解释原因、判断优先级并导出行动差异的结构。
