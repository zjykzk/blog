# Three Constraints for Building Products Source Guide

> Source: Jordan Lord, [3 Constraints](https://jordanlord.co.uk/blog/3-constraints/)

## What It Covers

Jordan Lord 把约束视为创造力的启动条件：约束通过缩小搜索空间，帮助建设者排除不值得做的方向，把注意力集中到少数真正重要的问题上。文章源于两类产品失败经验——产品过于复杂，或产品没有身份——并提出三个必须同时通过的建设门槛。

这三个门槛分别检查项目能否说清、投入能否积累、产品能否被辨认：

```text
一页纸              -> 压缩复杂度与歧义       -> 说得清
可分离的核心技术    -> 保留长期杠杆与原创性   -> 积得下
定义性产品约束      -> 限制功能膨胀、形成身份 -> 认得出
```

形式化地说，作者采用的是合取式准入规则，而不是从三条中任选一条：

```text
值得建设 = 一页纸清晰定义
        AND 核心技术可脱离当前产品继续存在
        AND 一条定义性约束贯穿用户体验
```

## Key Points

### 一页纸限制复杂度与歧义

- 每个产品想法都应先写成一页纸；它既是北极星，也是面向投资人、贡献者、团队成员和亲友的共同沟通基线。
- 团队出现冲突时，如果争议事项不在一页纸中，要么不值得争，要么重要到应该修改一页纸。
- 写不满一页，说明理解还不够，应回到研究、规划和原型；超过一页，说明项目过于复杂，不应直接建设。
- “一页”不只是排版限制，也可以理解为对认识压缩率的测试：一个方向是否已经清楚到能被有限文字完整约束。^[inferred]

### 可分离核心技术限制低杠杆项目

- 核心技术支持当前产品，但不等于当前产品；它必须能在产品转向或消失后继续存在。
- 作者对 tech 的用法很宽，包括 method、skill、tool，甚至另一个 product；因此更准确的中文理解是“可独立复用的核心能力”，而不只是算法或底层代码。
- 产品经常转向，核心能力却可以保持稳定并持续复利；Git、HCL 和 Kubernetes 是文章给出的例子。
- 一项想法如果不能推动这种长期能力积累，在作者的筛选框架里就不具备足够高的杠杆。

### 定义性约束限制功能膨胀并生成身份

- 每个产品都应选择一条位于前台、用户持续看得见并与之互动的约束。
- Minecraft 的“一切由方块构成”和 IKEA 的“平板包装、用户自行组装”都不是局部功能，而是贯穿产品的生成规则。
- 好约束通过持续排除选项，让界面、功能和体验从同一规则中长出来；产品因此获得一致的手感和可辨认的身份。
- 这条定义性约束也应写入一页纸，成为产品决策的显式边界。

## 核心技术与产品的关系

“核心技术必须与产品分离”不是让产品停止使用它，也不是要求一开始就拆成独立代码仓库。它要求建设者在认知和责任上分清两层：^[inferred]

```text
核心能力：稳定地完成什么
    |
    | 被选择、包装并嵌入工作流
    v
具体产品：为哪类用户，在什么场景，完成什么任务
```

核心能力解决可复用的“能力问题”；产品把这种能力组织成特定用户可以采用、理解并信任的完整体验。若更换界面、目标用户或使用场景后能力仍然成立，它就具有作者所说的独立生命。^[inferred]

这一区分也澄清了第二条和第三条约束的差别：

| 对象 | 回答的问题 | 用户必须直接感知吗 |
|---|---|---|
| 核心能力 | 我们长期积累什么独特能力？ | 不一定 |
| 产品设计 | 如何让特定用户完成特定任务？ | 是 |
| 定义性约束 | 为什么产品各部分像从同一规则中长出？ | 必须 |

例如在 Minecraft 中，体素世界生成、渲染和模拟可以视为底层核心能力；采集、合成、建造和生存组成产品设计；“一切由方块构成”则是塑造整个体验的定义性约束。^[inferred]

## 分离如何间接改善产品设计

文章直接论证的是长期杠杆与复利，并没有完整展开“分离如何改善设计”。下面的因果链是基于文章框架的进一步推论：^[inferred]

```text
能力与产品分层
    |
    +-> 技术输出不再自动等于产品界面
    |       -> 设计从用户任务选择能力的表达方式
    |
    +-> 稳定内核不被当前产品形态锁死
    |       -> 外层可以低成本试错、转向和重组
    |
    +-> 核心能力本身已经能工作
            -> 产品必须证明自己额外组织了什么价值
               -> 工作流、反馈、纠错、协作、权限与信任
```

### 避免把技术演示误当成产品

当能力和产品混在一起时，团队容易从“技术能输出什么”直接跳到“界面就展示什么”。例如，能生成知识图谱不等于用户想看知识图谱；用户可能真正需要的是快速理解报告、追溯证据或发现矛盾。^[inferred]

分层以后，产品设计必须增加一个转换步骤：先识别用户要完成的任务，再选择核心能力的合适表达。能力相同，面向研究者可以表现为资料关系图，面向投资人可以表现为尽调结论与证据链，面向客服则可以表现为可追溯问答。^[inferred]

### 用稳定内核换取产品试错自由

产品经常需要换用户、删功能或改变交互。如果能力与某一种界面和流程锁死，每次产品试错都会威胁全部技术投入，团队也更容易因为沉没成本保留错误设计。^[inferred]

核心能力可独立存在时，失败的是某一种产品表达，而不必是底层能力本身。稳定内核由此允许外层更大胆地变化，并让一次产品失败不至于清空全部积累。^[inferred]

### 迫使产品证明技术之外的价值

核心能力一旦可以单独描述，产品就必须回答：用户为什么不直接调用这项能力？产品的增量价值通常来自降低门槛、嵌入工作流、处理反馈与纠错、支持协作与权限，以及把通用输出转成特定场景中的可靠结果。^[inferred]

因此，分离并不会自动产生好设计；它只是建立了更好的设计问题：

> 除了展示技术能力，这个产品究竟替用户组织了什么？

## 判断边界

文章隐含“值得建设的产品应建立在某种可复用、可复利的独特能力上”。这个前提并非普遍成立。产品优势也可能来自品牌、社区、网络效应、渠道、供应链、服务流程或用户洞察，而不是一项可独立抽取的核心技术。^[inferred]

过早追求工程分离还可能制造“平台先行”：在尚未理解真实用户和重复场景之前，先建设通用框架，最后得到抽象漂亮但当前产品不好用的基础设施。^[inferred]

因此，更稳妥的使用方式是：

1. 先在认知上区分核心能力与当前产品表达。
2. 用多个真实场景检验能力是否真的重复出现。
3. 只有重复性和边界稳定后，再决定是否进行代码、团队或商业上的物理拆分。^[inferred]

一个实用的反事实检查是：

> 如果明天关闭当前产品，还剩下什么能够支持下一个产品？

有清晰答案，说明存在可积累的核心能力；没有答案，并不自动证明产品不值得做，但意味着它没有通过 Jordan Lord 这套偏长期复利的筛选标准。^[inferred]

## Open Questions

- 怎样判断一项能力已经跨过“多个真实场景验证”的门槛，值得工程化抽离？
- 当优势来自社区、品牌或供应链时，是否应把 core tech 扩展理解为“可复利核心资产”？
- 一页纸、核心能力和定义性约束发生冲突时，哪一条拥有最终裁决权？
