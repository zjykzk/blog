# AI Evals FAQ Source Guide

> 来源：[AI Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)

这份 FAQ 汇集作者在教授 5,000 多名工程师和产品经理时反复遇到的问题。它讨论的重点是 product evals：如何判断一个具体 AI 产品是否满足用户与业务要求，而不是如何用公共 benchmark 比较通用模型。

作者明确提醒，这些建议是“适用于多数情况的鲜明意见”，不是普遍定律。下文按“核心问题—概念结构—推理流程—变化机制”重组分散的问答；重组出的层次、机制链和进一步推论标为 `^[inferred]`。

## 核心问题

**团队如何知道 AI 产品哪里不好，并据此可靠地改进？**

这个问题包含三个相互依赖的困难：

1. **成功标准通常没有被完整说出。**“回答要好”“助手要有帮助”隐藏了大量业务要求，例如什么时候追问、何时转人工、哪些事实不能遗漏，以及工具真正成功前能否向用户宣布任务完成。
2. **真实错误难以提前穷举。**模型、prompt、retrieval、tools、应用代码和用户行为共同产生结果。公共 benchmark 只能帮助选择起点，不能证明产品在自身环境里可用。
3. **测量本身也可能出错。**通用的 helpfulness、coherence 或 similarity 分数可能与具体产品失败无关；团队若围绕错误代理指标优化，会得到“分数提高而用户体验没有改善”的结果。

文章把评估定义为对质量的系统测量。每项 eval 应检查相关案例中的一种行为，并返回分数或结构化审阅；一个产品通常需要多项 eval，因为它能以多种方式失败。

## 概念结构

文章的概念可以重组成一条从业务目标到持续改进的依赖链：^[inferred]

```text
用户目标与业务要求
        ↓
完整交互轨迹 Trace
        ↓
错误分析：观察具体失败 → 归纳失败类型
        ↓
质量标准 Rubric：什么算通过，什么算失败
        ↓
评估器：代码检查 / 人工判断 / 经验证的分类器
        ↓
修复、实验、回归检查、生产观察
        └────────── 新案例回到错误分析
```

### Model benchmark 与 product eval

- **Model benchmark** 用共享任务比较通用模型，可以帮助选出值得尝试的模型。
- **Product eval** 检查具体产品是否完成用户目标，范围包括模型、prompt、retrieval、tools 和应用代码。

取消订单 Agent 的评估不应只问回答是否流畅，而要检查：它是否选择了正确订单；是否等待取消工具成功；订单状态是否真实改变；是否在这些条件满足之后才告诉用户取消完成。

### Trace 与错误分析

Trace 是从初始用户请求到最终结果的完整记录，包括用户消息、模型响应、检索材料、工具调用、状态变化，以及复杂场景中的人工交接。

错误分析从代表性 traces 开始：

1. 收集真实交互；没有数据时可先生成合成样本。
2. 由懂业务的人做 open coding，对具体失败写开放式观察。
3. 用 axial coding 把相似观察归成 failure taxonomy，并统计每类失败。
4. 持续抽取高信息量案例，直到新审阅不再显著改变失败分类。

文章建议先人工审阅至少 30 条 trace，再让 LLM 帮助聚类；一个约 100 条的多样化工作池可以支持这轮人机协作。最小可行方案更轻：系统发生重大变化时，花 30 分钟审阅 20–50 个输出。

### Rubric、评估器与判断权

质量标准来自具体失败和领域专家判断。小中型团队可以指定一位“benevolent dictator”作为质量标准的最终责任人，以减少多人标注造成的停滞；多领域或跨文化产品才更需要多人标注与一致性测量。

评估器按条件选择：

- 客观状态优先用断言、数据库查询、执行测试、schema 或 regex。
- 需要语义判断时，使用人工审阅或分类器。
- LLM-as-a-Judge 也是分类器，必须拿可信人工标签验证。
- 每个 Judge 尽量只检查一种失败，例如“该转人工时是否转人工”，而不是一次评分整体对话质量。

作者推荐用 Pass/Fail 表达判断。二元标签迫使团队明确边界，减少 3 分与 4 分之间的主观漂移。需要呈现渐进变化时，可以把总体质量拆成多项二元检查，而不是退回模糊的 Likert 量表。

### CI、生产监控与 Guardrail

| 机制 | 作用 | 典型特点 |
|---|---|---|
| CI eval | 部署前防止已知错误复发 | 小而精的回归集；优先确定性检查 |
| 生产评估 | 在真实流量中发现失败并估计频率 | 抽样、异步运行、更多无参考答案的 Judge |
| Guardrail | 在请求路径上阻止高影响错误 | 快、可解释、低误拦截；会直接影响用户体验 |

生产中发现的新失败应加入 CI 数据集，形成从线上观察到离线回归的闭环。

## 推理流程

### 1. 先观察失败，再决定测什么

LLM 产品的失败面近乎无限，开发前无法可靠枚举。先写大量 evaluator 容易检测想象中的错误，却漏掉真实用户正在遭遇的问题。

因此，评估工作从错误分析开始，而不是从平台或指标开始。团队先读 traces，形成对产品的直接认识，再把高频、高影响问题写成明确标准。

### 2. 发现失败后，先修明显问题，再决定是否自动化

有些失败只是要求没有写进 prompt，有些是普通代码 bug。此类问题可以直接修复。自动 evaluator 值得用于会反复出现、需要多轮实验才能改善的 generalization failure。

不同评估方式成本差异很大：代码断言便宜；LLM Judge 往往需要 100 条以上人工标签、持续维护，以及工程师、产品经理和领域专家协作。是否建设 evaluator 应取决于错误影响、重复发生概率和长期迭代价值。

作者称其项目常把 60%–80% 的开发时间用在错误分析和评估上，其中主要工作是理解失败，而不是建设自动检查。

### 3. 用足够简单的方法检查明确条件

若条件能通过系统状态直接验证，就用代码。例如，Agent 创建联系人后查询数据库，检查恰好存在一条匹配记录。只有条件需要语义或业务判断时，才使用分类器或人工审阅。

这使评估结果保持可行动性：失败能够指向具体组件、规则或产品行为，而不是留下一个无法解释的综合分数。

### 4. 用人工标签检验自动评估器

Judge 的输出看起来稳定，不等于它可信。文章建议将带人工标签的数据分为：

- **Training set**：向评估器展示任务和示例；
- **Development set**：反复检查分歧，修改 prompt 或选择模型；
- **Test set**：隔离保存，在开发结束后检查未见数据上的泛化。

验证同时观察：

- **TPR / recall**：真实错误有多少被抓住；
- **TNR**：真实正确的输出有多少被放行。

人工与 Judge 不一致时，先检查 rubric 是否含糊、输入是否缺少证据、标签是否有误，以及 Judge 是否一次承担太多失败类型；这些问题解决后，再做 prompt tuning 或更换模型。

### 5. 复杂系统先看端到端结果，再找第一个上游失败

Agent 评估分两层：先把系统当黑盒，判断用户目标是否完成；确认失败后，再检查 tool choice、parameter extraction、error handling、context retention、效率和关键状态。

多步骤错误会向下游传播，所以先记录第一个上游失败。若多轮对话的错误可以简化为单轮复现，就优先调试单轮；只有错误依赖上下文时才保留多轮测试。

### 6. 让生产中的新发现进入下一轮评估

CI 保存核心能力、历史 bug 和已知边界；生产监控继续发现测试集尚未包含的问题。确认后的代表性案例进入回归集，新的错误分类则推动 rubric、prompt、检索或产品流程改变。

## 变化机制

以下机制把 FAQ 中分散的操作建议还原成产品变化过程。它们属于基于原文的结构化推演。^[inferred]

### 1. 具体案例使隐含要求外显

```text
看到意外输出 → 专家说明哪里不对 → 暴露未表达要求
→ 更新 rubric / prompt / 产品流程 → 系统行为改变
```

人工审阅同时改变产品和团队对产品的理解。文章将这种“看过输出后成功标准发生变化”的现象称为 criteria drift。自动 prompt 优化可以追逐既有指标，却无法单独发现团队尚未认识的新失败。

### 2. 评估器质量决定反馈方向

```text
标准更明确 + 证据更充分 → Judge 误判减少
→ 实验结果更可信 → 修改方向更准确
```

TPR 与 TNR 的权衡必须结合错误基准率和业务代价。错误稀少时，即使误报率不高，人工审核队列也可能主要由假警报组成；高风险场景可能更重视漏检，创作场景则可能更怕误拦截。^[inferred]

### 3. 降低审阅摩擦会提高学习速度

```text
证据集中展示 + 符合领域的呈现 + 快捷操作
→ 单例审阅成本下降 → 专家能深入检查更多案例
→ 更快形成失败分类并验证修复
```

因此，文章把定制 annotation interface 视为高杠杆投资：邮件按邮件呈现，代码使用高亮，相关上下文放在同一屏，次要工具输出折叠，并提供键盘操作和进度提示。

可验证性还会反过来改变产品设计。例如，与其要求医生直接审查一篇长报告，不如先展示带来源的事实和冲突，让医生在生成报告前纠正中间结果。

### 4. 修复上游错误会改变下游失败分布

```text
理解需求错误 → 检索错误 → 生成错误 → 动作错误
```

修复第一个上游错误可能同时消除多项下游症状；上游改善后，更多请求能走到后续阶段，下游原本被遮住的问题又会显现。因此，持续改进会让主要失败位置迁移，新的失败热点未必代表总体退步。^[inferred]

### 5. 评估挑战必须随产品演化

测试集长期全部通过时，它对下一步改进提供的信息会减少。团队应通过新的 error analysis 增加真实用户行为、困难案例和新要求，也可以降低饱和评估的运行频率或将昂贵 Judge 退休。

测试集或成功标准改变后，历史分数不再天然可比。一次通过率下降可能来自产品退步、案例变难或标准变严；长期趋势需要结合流失率、活跃用户或收入等产品指标解释。^[inferred]

## 方法边界

- 单一质量负责人适合多数小中型团队，但跨专业、跨语言和跨文化产品可能需要多个标准制定者。
- 通用指标不适合作为最终质量判断，却可以作为筛选信号，帮助找到值得人工审阅的 traces。
- 使用同一个模型完成任务和充当 Judge 并非自动无效；是否可用应由 held-out 人工标签上的 TPR/TNR 决定。
- 给 Judge 更多上下文不一定更好。只提供判断该失败类型所需的证据，并用消融实验检查无关上下文是否造成干扰。
- 评估器通常异步运行；只有满足延迟、成本和误拦截要求的检查，才适合进入同步 Guardrail。
- 模型切换不应成为默认改进轴。错误分析应先证明模型本身是主要原因。

## Open Questions

- 当 rubric 与测试集持续变化时，如何对评估版本做严格管理，并把产品变化、案例难度和标准变化分开？
- 当领域专家成为质量判断瓶颈时，怎样扩展审阅能力而不切断专家与真实失败之间的联系？
- 如何发现生成模型与 Judge 共享的盲点，而不是只测二者对同一 rubric 的一致性？
- 如何证明某项 eval 的改善对用户行为和业务结果具有因果贡献，而不只是相关？
