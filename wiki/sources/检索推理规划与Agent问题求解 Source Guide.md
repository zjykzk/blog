## Capture Policy

## What It Covers

对话围绕一个总判断展开：**大模型（LLM）只是一个认知/推理引擎，真正的智能是一个完整的问题求解闭环**——目标 + 状态 + 记忆 + 检索 + 推理 + 规划 + 行动 + 反馈。沿途澄清了六组核心区分：检索找已有信息、推理产生新结论；推理不是简单模式匹配但建立在模式学习之上；规划是面向目标、从目标倒推行动序列的推理；上下文学习不等于推理；上下文是工作记忆载体、记忆是更广的持久化机制；状态是决定未来所需的充分信息、是对历史的压缩、不等于世界本身。

它和 [[wiki/concepts/Agent]]、[[wiki/concepts/Agentic Control Loop]]、[[wiki/concepts/Reasoning as Structure Mapping]]、[[wiki/concepts/Neural Network Inference Boundary]] 处在同一知识簇。

## Preserved Content

### 1. 检索 vs 推理：找节点还是建边

可以把**检索（Retrieval）**和**推理（Reasoning）**理解成两种完全不同的认知操作：

> **检索：从已有的信息空间中找到答案。**
> **推理：根据已有信息，通过规则或关系推出新的结论。**

**最核心的区别。** 问「爱因斯坦什么时候获得诺贝尔物理学奖？」——去知识库/搜索引擎找到「1921 年」，这是检索。若知道「诺贝尔奖授予的是 1921 年的奖项 / 爱因斯坦 1922 年实际领取」，得出「爱因斯坦获得的是 1921 年诺奖，但 1922 年才正式领奖」，这里就包含了推理/整合。

**从信息流角度：**

```text
          外部信息空间
               │
               │ 检索
               ▼
        ┌─────────────┐
        │ 已存在的信息 │
        └─────────────┘
               │
               │ 推理
               ▼
        ┌─────────────┐
        │ 新的结论/判断 │
        └─────────────┘
```

**检索主要是在"找已有东西"，推理主要是在"产生新的东西"。**

更典型的例子：问「小明今天为什么没来上班？」数据库里若有「小明请假，原因发烧」，直接找到即检索。若数据库只有「小明今天没打卡 / 昨天说身体不舒服 / 今天是工作日」，你推断「小明可能因身体不适没来」，这是推理。注意「可能」很重要——**推理的结果不一定是事实，它是从事实推导出来的结论。**

**二者解决的问题不同：**

| | 检索 | 推理 |
|---|---|---|
| 核心问题 | "哪里有这个信息？" | "这些信息意味着什么？" |
| 操作 | 查找、匹配、召回 | 分析、演绎、归纳 |
| 输入 | 信息需求 | 前提/事实 |
| 输出 | 已存在的信息 | 新的结论 |
| 是否产生新知识 | 通常不产生 | 可以产生 |
| 典型技术 | 搜索、倒排索引、向量检索、数据库查询 | 逻辑推理、数学推导、因果分析、规划 |

**现实中的 AI 往往两者结合。** 问「为什么秦国最后能统一六国？」AI 先检索（商鞅变法、军功爵制、关中地理、远交近攻、长平之战……），再推理（商鞅变法 → 提高国家组织和动员能力 → 军事优势 → 兼并战争扩大 → 六国无法结成稳定联盟 → 秦国统一）。

> **检索提供"事实材料"，推理负责"建立事实之间的关系"。**

这就是 RAG（检索增强生成）背后的思想：不要让模型只依赖自身记忆，先把相关事实检索出来，再基于这些事实推理。

**更深一层：知识 vs 关系。**

> **检索是在寻找"节点"，推理是在建立"边"。**

检索分别找到 A=商鞅变法、B=军功爵制、C=秦国富强、D=统一六国；但回答"为什么"需要建立 `A→B→C→D` 这些箭头——它们就是推理、因果关系、解释结构。所以：

> **检索解决"我知道什么"；推理解决"这些东西之间是什么关系，以及由此能推出什么"。**

这也是为什么一个 AI 系统即使拥有很强的检索能力，也不一定具有很强的推理能力。

### 2. 大模型会推理吗：会，但不是"查数据库"

> **大模型确实能推理，但它的推理本质上不是"查数据库"，而是在生成过程中进行一系列内部计算，从已有信息构造出新的中间结论。**

给它「所有 A 都是 B / 所有 B 都是 C / 小明是 A，问：小明是什么？」它能得到「小明 → C」，而「小明是 C」并没有直接出现在输入里，是根据命题关系**计算出来的**——这就是推理。

传统程序是明确执行规则（`if A: B`）；大模型则更像：

```text
输入 → 神经网络计算 → 中间表示 → 继续计算 → 新的中间表示 → 最终输出结论
```

所以大模型的"推理"不是"从数据库找规则→执行规则"，而是**通过神经网络中的大量参数和逐步生成的 token，对输入信息进行变换和组合**。

可以把大模型能力拆成两支：**记忆/知识**（"商鞅变法哪一年"，主要依赖记忆）与**推理**（"为什么商鞅变法能增强秦国战争能力"，需要把 变法→军功爵制→激励军事行为→动员能力增强→军事竞争力提高 串起来）。

**"LLM 只是预测下一个 token"对吗？** 对，但容易误解。训练目标确实是根据前文预测下一个 token，但"预测下一个 token"是训练目标，不等于"模型内部只能做简单词语匹配"。为稳定输出 `3`，模型内部可以形成类似 `1 + 2 ↓ 3` 的计算结构。**next-token prediction 可以产生推理能力**——简单的训练目标，可以涌现出复杂的计算能力。

但它的推理不是无限可靠的：算术错误、逻辑错误、前提理解错误、中间步骤错误、"看起来合理但实际错误"的结论都可能发生。

> **"大模型会推理" ≠ "大模型永远能正确推理"。** 这和人类类似：人也会推理，但会犯逻辑错误。

三层结构：AI 问题求解 = 检索（找到已有事实）+ 推理（产生新结论）→ 行动。现代 Agent 真正有意思的地方不是"大模型会不会推理"，而是**如何让"检索→推理→行动→新信息→再推理"形成一个闭环**。

### 3. 推理的严格定义

> **推理（reasoning）是：在给定信息、规则、目标或约束的基础上，通过有结构的中间步骤，得到原本没有直接给出的结论、判断或行动依据的过程。**

关键词：

1. **"给定信息"**——推理必须有输入（前提：所有人都会死亡；苏格拉底是人）。
2. **"中间步骤"**——不是把输入换种说法，而是：所有人都会死亡 → 苏格拉底属于"人" → "人"属于会死亡的集合 → 苏格拉底会死亡。中间结构使结论能被**从前提中导出**。
3. **"得到新的结论"**——这是推理和检索最重要的区别。检索：数据库→找到"苏格拉底会死亡"；推理：从"所有人会死亡 + 苏格拉底是人"产生它。**结论没有直接作为事实提供，而是由已有信息产生。**
4. **"不一定是绝对正确"**——「小明昨天没来、今天没来、昨天说不舒服」→「小明可能生病了」仍是推理，只是属于**不确定推理**而非严格演绎。所以 **推理 ≠ 正确答案**，而是**按照某种规则，从已有信息产生结论**。

**抽象成函数。** 设 `I`=已知信息、`R`=推理规则、`C`=约束、`G`=目标，则 **Reasoning(I, R, C, G) → Conclusion**。

**更深的计算/认知定义：**

> **推理是对内部表示进行有约束的变换，使系统能够从当前已知状态获得新的、对任务有用的信息。**

`A>B, B>C` 经推理得 `A>C`，系统知识状态从 Knowledge₀ 变为 Knowledge₁，且 `Knowledge₁ ⊃ Knowledge₀`。这就是为什么**检索主要是获得信息，推理主要是产生信息**。

由此区分几个易混概念：

| 操作 | 本质 |
|---|---|
| 检索 | 找到已有信息 |
| 记忆 | 保存/调用已有信息 |
| 推理 | 从已有信息产生新结论 |
| 规划 | 从目标推导行动序列 |
| 决策 | 在多个行动中选择一个 |
| 行动 | 改变外部世界状态 |

压缩成一句：**推理，就是依据已有信息和规则，对信息进行结构化变换，从而得到新的结论或行动依据。**

### 4. 真的推理还是复杂模式匹配

> **"大模型的推理到底是真的推理，还是复杂的模式匹配？"** 关键不在于二选一，而在于：模式匹配和推理之间到底是什么关系。

极端观点：只是模式匹配。训练目标就是预测下一个 token（`1 + 1 =` → `2`），有人认为"它只是记住了模式"。但 `17,382 × 4,291 = ?` 很可能没在训练数据里原样出现，模型仍可能通过内部计算得到结果——**仅把推理解释成"记忆答案"是不够的**。

关键实验：组合新知识。告诉模型 `A>B, B>C`，问 A 和 C 谁高，答 A。这个关系可能没在输入中直接出现，因此至少存在某种**组合（composition）**：已有关系 → 组合 → 新关系。这已具有推理的基本特征。

**但"模式匹配"和"推理"不是互斥的**——这是最重要的一点。人类推理也不凭空产生（鸟→有翅膀→会飞）。真正的区别不是"模式匹配 vs 推理"，而更接近一条谱系：

```text
简单模式匹配 → 组合模式 → 规则化变换 → 多步推理
```

**直接映射 vs 计算。** 「法国首都是什么」接近 `输入→记忆/模式→输出`；「A>B>C>D 谁最高」需要多步关系变换，存在某种 **in-context computation（上下文中的计算）**。

**Chain-of-Thought 为什么重要。** 让模型一步步思考往往比直接回答更容易正确（100×0.8=80，80×1.25=100）。中间过程提供了额外的计算空间。可理解成**把复杂计算分解成多个较简单的状态转换**：`S₀ → 计算 → S₁ → 计算 → S₂ → … → Sₙ → 输出`。这和传统程序 `S₀→f₁→S₁→f₂→S₂` 在抽象结构上相似，区别在于：**传统程序的变换规则由程序员显式定义；大模型的变换规则主要隐含在参数中**——所以可理解成"隐式程序"。

**系统性泛化（Systematic Generalization）** 的问题：学了 `A>B, B>C` 后应能处理 `X>Y, Y>Z`。现代 LLM 在很多任务上确实表现出这种能力，但并不完美，结构稍变可能突然犯奇怪错误。所以更准确的说法是：**LLM 表现出了真实的计算与推理能力，但这种能力不等同于传统形式逻辑系统那种严格、稳定、可验证的推理。** 因为它的"规则"不是 `∀x,y,z: x>y ∧ y>z → x>z` 这种符号规则，而是分布在数千亿参数、高维表示空间和大量统计结构中——它的推理更像**在一个巨大参数化函数中进行计算**，而不是**调用一个明确的逻辑推理机**。

三层结构：LLM = 知识记忆（"知道什么"）+ 计算能力（"能推出什么"）→ 推理。**参数提供知识和先验结构，Transformer 提供计算机制，上下文提供当前问题和临时状态**，三者组合才形成 reasoning。

结论：**大模型的推理不是简单的模式匹配，但它的推理能力建立在模式学习之上。** 更精确：**"模式匹配"是材料，"计算/组合"是过程，"推理"是我们从这种过程得到的功能性描述。**

什么才算"真正的推理"？若定义"推理 = 根据已有信息，通过规则产生新结论"，大模型显然可以推理；若要求"必须用显式符号规则，且每一步可形式验证"，普通 LLM 就不完全符合。真正值得讨论的问题变成：**推理的本质究竟是"符号规则的执行"，还是"对内部表示进行受约束的计算变换"？** 后一定义下，神经网络推理完全可以是真正的推理。这也是为什么越来越多 AI 系统走向 `LLM + 检索 + 代码执行 + 形式验证 + 搜索 + 规划器 + 环境反馈`——单纯依靠神经网络的"隐式推理"能力很强，但可靠性和可验证性不足。

### 5. 大模型作为认知引擎 vs 问题求解系统

> **大模型本身更像一个"认知引擎"，而 Agent / 问题求解系统则是一个完整的"问题求解闭环"。**

一个系统解决问题最基本的过程：问题 → 理解问题 → 知道需要什么信息 → 获取信息 → 形成假设 → 推理 → 采取行动 → 观察结果 → 修正 → 继续行动 → 达到目标。

"怎么让服务 P99 从 500ms 降到 100ms？"不是单纯问答，系统需要：了解当前系统 → 获取监控 → 发现 P99 主要来自 DB → 分析 DB 查询 → 假设索引不合理 → 改索引 → 压测 P99=180ms → 继续分析 → 缓存命中率低 → 优化缓存 → P99=90ms → 完成。

**和"回答问题"的区别**——理解 Agent 最重要的一点：普通问答是 `问题 → 答案`（Redis 为什么快 → 因为基于内存……结束）；问题求解是 `目标 → 状态 → 行动 → 新状态 → 行动 → …… → 目标达成`。这里出现了**状态（State）**。

**问题求解的核心是"状态空间搜索"。** `S0=当前问题状态`，可采取不同动作（查库/看日志/看监控/改配置/重部署），每个动作产生新状态，最终寻找 `S0 → S3 → S7 → S12 → Goal` 这样一条路径：

> **问题求解，本质上可以看成在状态空间中寻找一条从"当前状态"到"目标状态"的路径。**

**大模型负责什么？** 它不是整个问题求解系统，更像其中的**决策/认知模块**：状态/行动/目标 → 大模型（理解/推理/规划）→ Tool（搜索/DB/API）。

**为什么需要检索？** 模型自身知识有限且可能过时（"过去 24 小时为什么发生 3 次超时"模型不可能凭空知道）。所以 `LLM → 提出信息需求 → 检索（日志/监控/Trace/DB/代码/配置）→ 返回证据 → LLM 推理`。**检索给推理提供世界状态**——这句话很重要。

**为什么还需要行动？** 很多问题不能只靠观察解决（磁盘快满：清理旧日志 → 95%→72%）。于是问题求解从"感知→思考"变成"感知→思考→行动→感知→思考→…"，这就是 Agent 的核心。

**Agent 是一个闭环：** Goal → Observe → Reason → Plan → Act → Observe(新状态) → …，即经典的"感知→决策→行动→感知"循环。

**问题求解其实是在不断减少"不确定性"**——最值得理解的一层。一开始"服务延迟为什么升高"有 A(DB)/B(Redis)/C(网络)/D(CPU)/E(GC)/F(下游) 六种可能，处于高不确定状态。检索 CPU 正常排除 D，GC 正常排除 E，Trace 显示 80% 耗在 DB → A↑↑，继续调查 DB 发现某 SQL 延迟异常 → 索引缺失 → Root Cause。问题空间从很大逐步收窄到一个点：

> **问题求解系统的一个核心功能，就是通过观察、检索、推理和行动，不断缩小可能状态空间。**

**为什么"Agent"比"Chatbot"复杂。** Chatbot：`Input → LLM → Output`，主要任务是"生成一个好的答案"；Agent：`Goal → Reason → Plan → Act`（带 Observe 回环），主要任务是**改变世界状态，使世界从当前状态到达目标状态**。"帮我把这个 Bug 修掉"——Chatbot 给一段修复代码；Agent 读代码→理解架构→定位 Bug→改代码→跑测试→失败→分析原因→再改→测试通过→完成。后者才是真正的问题求解系统。

**统一模型：**

```text
                    ┌─────────────┐
                    │    Goal     │  目标
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │    State    │  当前状态
                    └──────┬──────┘
                           ↓
        ┌──────────────────┴──────────────────┐
        ↓                                     ↓
     Retrieval 获取信息                    Reasoning 理解/推理
        └──────────────────┬──────────────────┘
                           ↓
                        Planning 规划
                           ↓
                         Action 行动
                           ↓
                     World changes 世界改变
                           ↓
                        Observe 观察
                           └──────────→ State
```

因此，**大模型只是这个系统里的"Reasoning Engine"之一**。真正完整的"智能"更接近：**目标 + 状态 + 记忆 + 检索 + 推理 + 规划 + 行动 + 反馈**。这已经从"语言生成"跨到了"智能行为"。而"检索 vs 推理"正是这个体系里关键的一条分界线：**检索是在扩大系统所知道的世界；推理是在已有世界模型上计算；行动是在现实世界中改变状态。**

### 6. 规划 vs 推理：面向目标的推理

> **规划通常是推理的结果之一，但"规划 ≠ 推理"。更准确地说：推理负责判断"应该怎么做"，规划负责把这个判断组织成"具体做什么、按什么顺序做"。**

目标：把 P99 从 500ms 降到 100ms。先**推理**：P99=500ms → Trace 显示 70% 耗在 DB → 慢查询集中在 SQL A → SQL A 没用有效索引 → 判断主要瓶颈是 SQL A（得到"应优先解决 SQL A 的索引问题"，这是推理结果）。再**规划**：1.分析执行计划 2.确认索引方案 3.创建索引 4.灰度流量 5.观察 P99 6.若仍 >100ms 继续分析。

**但规划本身也包含推理**（"先创建索引还是先修改 SQL"需要比较方案的成本/风险/收益/依赖/顺序），这个过程本身就是**规划推理（planning reasoning）**。

**推理是一个更大的概念**，可看成总类：

```text
推理
├── 因果推理 —— 为什么发生？
├── 演绎推理 —— 根据规则能推出什么？
├── 归纳推理 —— 从多个案例总结规律
├── 诊断推理 —— 什么原因导致当前现象？
├── 预测推理 —— 接下来可能发生什么？
└── 规划推理 —— 为达到目标应采取什么行动？
```

所以**规划可被看成一种面向行动的推理**。

**一个特别关键的区别：** 普通推理是"从事实推出结论"（`A→B, B→C, 所以 A→C`）；规划是"从目标反过来寻找行动路径"（目标 P99<100ms ← 需要 DB 延迟<50ms ← 需要 SQL A<10ms ← 需要加索引 ← 需要先确认执行计划）。**普通推理更多在解释"世界是什么样"；规划在寻找"世界应该如何变化"。**

数学形式：**推理 `S → 判断`；规划 `S + Goal → Action Sequence`；行动 `S + Action → S'`。**

> **Reasoning 是"认知"，Planning 是"面向目标的认知"，Action 是"把认知作用于世界"。** 这比简单地把 Agent 理解成"LLM + Tools"要深一层。

### 7. 为什么需要规划

因为**只推理出"应该做什么"还不够，复杂问题需要决定"先做什么、后做什么、做到什么程度，以及失败后怎么办"**。更本质地说：

> **规划存在，是因为目标状态和当前状态之间通常隔着多个动作，而且动作之间存在依赖、不确定性和代价。**

**最简单的情况：不需要规划。** 「2 + 3 等于多少」一个动作就结束，此时 **Reasoning ≈ Action**。

**复杂问题：一个动作无法直接到达目标。** 「把这个 Bug 修掉」：读代码→定位→假设→改代码→跑测试→发现新问题→再改→测试通过。当前状态到目标状态不是一步能完成，于是需要**规划一条状态转移路径**：`当前状态 S₀ + 目标 G → Planning → A₁→A₂→A₃→A₄`。所以规划本质上在解决"如何从 S₀ 到达 G？"。

**为什么不能每步都"现想现做"？** 简单任务可以（reactive 反应式：观察→推理→行动→观察→…）。但复杂任务里**当前最好的动作，可能取决于未来几步**。走迷宫：只看眼前 A 看似更近，但 A→死路，而 B→C→D→出口。所以需要考虑当前动作对未来状态的影响。

**规划解决"长程依赖"。** `A₁→A₂→…→A₆` 中 A₁ 的价值可能直到 A₆ 才体现（先读配置文件本身没解决问题，但可能导致：发现 feature flag → 发现功能被关闭 → 打开 → 测试 → 解决）。**规划让系统能够为了未来的目标，执行当前暂时没有直接收益的动作。**

**规划处理"动作依赖"。** 部署服务必须 编译→测试→构建镜像→推送→部署，不能颠倒，因为动作之间存在 **Precondition（前置条件）**（Deploy 需要 ImageExists=true，BuildImage 需要 BuildPassed=true）。规划就是在发现和组织这些依赖。

**规划处理"资源和代价"。** 三个方案（重启：低成本/中风险/效果不确定；扩容：高成本/低风险/高效果；重构：极高成本/高风险/长期）。目标不只是"找到能成功的方法"，而是**找到满足目标约束的较优路径**：`目标+约束+成本+风险+可用资源 → 最优/可接受路径`。这已接近经典的**搜索 / Optimization（优化）问题**。

**规划是在"未来空间"里推理。** 普通推理 `现在的事实 → 结论`；规划 `现在 → 假设执行 A → 未来状态 S₁ → 假设执行 B → 未来状态 S₂ → … → 目标`。所以**规划本身其实也是推理，只是它推理的对象变成了"可能的未来状态"**。Planning = 对行动和未来状态进行推理。

压缩成一句：**复杂目标不能通过一次行动直接实现，行动之间又存在顺序、依赖、代价和不确定性，所以系统必须在行动之前或行动过程中，对未来可能的状态和行动序列进行推演。** 推理("做 A 会发生什么？")+ 规划("为达到 G，应该 A→B→C 还是 A→D→E？")+ 行动("现在执行 A")结合起来，才让 Agent 从"回答问题的模型"变成"解决问题的系统"。

### 8. 上下文学习 vs 推理

要区分**上下文学习（in-context learning, ICL）**和**推理（reasoning）**，它们高度相关但不是同一概念：

> **上下文学习是"从当前上下文中调整/构造处理问题的方式"；推理是"利用这些信息和规则产生新的结论"。上下文学习可以为推理提供能力，但上下文本身不等于推理。**

**什么是 Agent 的上下文学习？** 给 Agent 任务 + 规则（先看调用链→再看错误日志→最后看最近变更）+ 示例（过去一个 Bug 是缓存失效），Agent 在**不修改模型参数**的情况下，从上下文形成临时的"任务理解 + 工作规则 + 案例经验"，应用到当前任务。这就是典型的 ICL。与传统机器学习的区别：传统学习 `数据→训练→修改参数 θ→模型获得能力`；ICL `上下文→模型内部计算→当前任务形成临时策略→输出`，**参数没有被更新**。

**它是不是推理？** 看具体过程。上下文告诉 Agent「发现 SQL 没用索引，先检查执行计划」，当前遇到「SQL A 延迟 500ms，执行计划全表扫描」，Agent 得出「应先检查索引」——`上下文规则 + 当前事实 → 结论`，**是推理**。但"从上下文中学到'遇到全表扫描先检查索引'这个策略"本身更准确地叫**上下文学习**。

两个不同维度：Context Learning 回答"怎么处理这个问题？"（获得策略）；Reasoning 回答"这个结论怎么来的？"（得出结论）。从三个例子（Redis 延迟→查慢命令 / DB 延迟→查慢 SQL / 网络延迟→查 Trace）抽象出"发现瓶颈→找对应观测工具"是上下文学习；实际遇到"P99 上升，Trace 显示 DB 占 80%"得出"DB 是主要瓶颈→查慢 SQL"是推理。

**Agent 的上下文像"临时程序"。** System Prompt + 任务 + 历史对话 + 工具描述 + 代码 + 检索结果 + 之前的执行结果，组合成**当前 Agent 的临时工作环境**：`Context = 知识 + 规则 + 状态 → LLM → 当前决策/推理`。所以 Agent 的上下文不是简单"聊天记录"，它承担了：工作记忆、临时知识库、任务状态、操作规则、历史经验、中间推理结果。

**为什么 Agent 特别依赖上下文？** 因为任务通常不是一次完成的。Coding Agent 修 Bug 分三轮，第二轮必须知道"我之前看过什么、做了什么、为什么这么做、测试结果、现在状态"。**上下文实际上成为 Agent 的"工作记忆"。**

可把上下文分成：Knowledge（世界知识）、State（当前任务状态）、History（已做过什么）、Rules（应该怎么做）、Evidence（检索/工具得到的证据）。运行时 `Context → Reasoning → Plan → Action → New Evidence → Context 更新 → Reasoning`。所以**上下文学习不是 Agent 的"推理模块"，而是让推理能够持续进行的工作记忆机制**。

**"Agent 为什么会越来越聪明"。** 参数 θ 是训练阶段的长期能力，Context Cₜ 是当前任务的临时知识，行为可粗略表示为 `Actionₜ = f(θ, Cₜ)`，`Cₜ₊₁ = Update(Cₜ, Observationₜ)`，形成 `Context → LLM → Action → Environment → Observation → Context` 的**运行时学习循环**。

划分：

| 概念 | 核心问题 |
|---|---|
| 训练学习 | 模型参数发生了什么变化？ |
| 上下文学习 | 当前上下文让我形成了什么临时策略/表示？ |
| 检索 | 我现在需要哪些外部信息？ |
| 推理 | 根据已有信息，我能推出什么？ |
| 规划 | 为达到目标，我应该采取哪些步骤？ |
| 行动 | 我实际做什么？ |
| 反馈 | 行动后世界发生了什么？ |

最准确的判断：若"上下文学习"指从上下文中发现规律、归纳规则，那么这个过程本身包含推理；若指利用上下文临时改变模型行为方式，那么它是一个更大的机制，其中可以包含推理，但不能等同于推理。对 Agent 来说真正有意思的是：**它把上下文从"输入文本"变成了一个不断变化的工作记忆，而推理是在这个工作记忆上持续进行的计算。**

### 9. 上下文 vs 记忆

> **可以说"上下文承担了记忆的功能"，但严格来说，上下文不等于记忆。**

**为什么说上下文像记忆？** Agent 在当前任务中可通过上下文"记住"：之前发生/发现/做了什么、结果如何、现在基于什么继续。这些信息进入 context（用户任务、已读代码、已发现问题、已执行操作、测试结果、中间结论）。所以 **Context 可以充当 Agent 的工作记忆（working memory）**。

**但"记忆"和"上下文"仍是不同概念：**

```text
                 Memory  "系统保存的信息"
        ┌──────────┴──────────┐
   短期/工作记忆            长期记忆
     Context              Memory Store
   当前任务可见          当前任务之外仍保存
```

Context：「刚才测试失败，错误在 foo.go:123」，任务结束后可能消失。长期记忆：「这个项目的测试通常需要先启动 Redis」，下次做完全不同任务时仍可检索。

**Context 更接近"工作记忆"。** 人脑：长期记忆 → 提取当前需要的信息 → 工作记忆 → 当前思考 → 行动。Agent：`Long-term Memory → Retrieval → Context → Reasoning → Action → Observation → Context 更新`。

> **Memory 是"保存信息的能力/机制"；Context 是"当前正在被模型使用的信息状态"。**

Agent 做了 100 个动作，不可能永远把全部历史塞进 Context，所以需要：`历史事件 → 压缩/总结 → 长期记忆 → 需要时检索 → 重新进入 Context`。

所以最准确的说法不是 `Context = Memory`，而是：**Context 是 Agent 的工作记忆载体；Memory 是更广义的信息持久化机制。** 再往前一步会碰到更关键的问题：**Agent 真正的"状态（State）"究竟是什么？** 因为 Context、Memory、State 三个概念很容易混在一起，但它们处于三个不同层次。

### 10. 状态 State：决定未来所需的充分信息

> **状态，是在某个时刻，描述一个系统为了决定"接下来会发生什么"而必须知道的全部相关信息。** 换句话说，状态 = 系统当前"处于什么情况"。

**先不用 AI 看状态。** 红绿灯：当前红灯 → 等待 → 绿灯。知道当前是红/绿灯就能预测接下来允许发生什么：`Stateₜ + Actionₜ → Stateₜ₊₁`。这就是状态的核心。

**状态不是"所有信息"。** 象棋当前局面（棋盘+棋子位置+轮到谁+特殊规则状态）构成状态；"昨天你和朋友下过什么棋"通常不是当前状态。所以状态不是**系统拥有的全部信息**，而是**决定系统未来行为所需要的当前信息**。

**数学形式：** `Sₜ₊₁ = T(Sₜ, Aₜ)`，T 是状态转移函数（余额 100 → 消费 30 → 余额 70，即 S₀=100, A₀=消费30, S₁=70）。

**回到 Agent。** Coding Agent 修 Bug 时状态可能是 `{任务:修复登录Bug, 分支:feature/login, 已改文件:[auth.go], 测试:失败, 错误:TestLoginExpired, 假设:token 过期处理错误}`，执行"修改 auth.go"后环境变化 → State₁ 中测试:通过、错误:无。即 `State₀ → Action:修改代码 → Environment → State₁`。

**Context 是不是 State？不是**，但高度相关：

```text
          Agent State
       ┌──────┴──────┐
   Environment     Internal State
      State            │
                    Context
                       │
                  LLM 可见部分
```

- **Environment State**（环境状态）：auth.go 当前内容、数据库当前数据、Git 当前 commit、测试当前结果——真实世界。
- **Agent State**（内部状态）：Agent 当前认为"Bug 大概率在 token expiration / 下一步该看 auth.go"。
- **Context**：真正送给 LLM 的（用户任务 + 相关代码 + 错误日志 + 之前操作 + 当前结论）——模型当前可访问的工作信息。

三者关系的闭环：`Environment State --Observation--> Agent State --Context construction--> Context --LLM reasoning--> Action --> Environment State'`。

**状态是"充分信息"。** 控制论、强化学习、规划里常隐含：**如果知道当前状态，就足以决定未来如何演化，而不必知道完整历史**（当前棋盘 > 过去 100 步棋谱）。因此**状态是对历史的一种压缩**——一个很深的观点。

**这解释了 Agent 为什么需要"记忆"。** 历史很长时全塞进 Context 很昂贵，Agent 会把历史压缩成当前状态（Bug 位于 auth.go / 已试方案 A 失败 / 方案 B 未试 / 测试仍失败）。所以 **Memory 的一个重要作用就是帮助 Agent 从过去的信息恢复/构造当前状态**。

**最关键的一层：状态 ≠ 世界本身。** 状态是一种**抽象**。现实世界（整个公司/所有员工/所有代码/所有数据库/所有历史……）不可能全部表示，于是针对某个问题选择"与当前问题相关的信息"构造 State：**状态不是世界本身，而是为了某个问题而对世界进行的充分抽象。**

**把整个 Agent 串起来：**

```text
世界 → State("当前处于什么情况") → Observation("我观察到了什么")
     → Context("我现在知道什么") → Reasoning("这意味着什么")
     → Planning("接下来怎么做") → Action("实际做什么")
     → 世界 → 新 State
```

- **Memory**：保存过去的信息
- **Retrieval**：从记忆/外部世界找信息
- **Context**：当前交给模型处理的信息
- **Reasoning**：对这些信息进行计算
- **Planning**：从目标倒推行动
- **Action**：改变世界
- **State**：描述当前世界/系统处于什么情况

其中最值得注意的：**Context 是"模型看到的东西"，State 是"系统实际上处于的东西"，二者可能完全不同**。一个优秀的 Agent，本质上就是在努力让"自己对 State 的理解"尽可能接近"真实 State"。这引出 Agent 核心问题：**Agent 怎么知道自己对当前 State 的理解是对的？**——自然进入 Observation、Evidence、Feedback 和 Evaluation。

### 11. 通用问题求解模型的收敛

（用户提出把"理解、检索、推理、行动"作为核心过程，"环境、工具、记忆"作为支撑系统。）

调整：**"理解、检索、推理、行动"是核心认知/行为过程；"环境、工具、记忆"是支撑这些过程的外部/内部系统。** 关键修正：**这四个动作不是严格的线性流水线，而是一个循环。**

- **理解**：把模糊请求（"这个服务最近很慢，帮我解决"）转成明确的 Problem/Goal/State（目标:降低延迟；现象:变慢；成功标准:P99<100ms；范围:某服务；约束:不能停机）。
- **检索**：产生信息需求（P99 曲线/Trace/慢查询/CPU/GC/最近发布），通过数据库/日志/搜索/代码/监控/知识库获取。**检索是为了降低对当前状态的不确定性。**
- **推理**：从获得的信息（CPU 正常/GC 正常/DB latency↑/Trace 80% 在 DB）产生新的知识/假设/判断（DB 是瓶颈 → 检查慢 SQL → SQL A 全表扫描 → 可能缺索引）。
- **行动**：有了判断后改变世界（改索引 → 跑测试 → 灰度 → 观察 P99）。Agent 不再只"认识世界"，而是在"改变世界"。

**环境、工具、记忆放哪里？** 它们不和"理解/检索/推理/行动"同层级。更好的画法是：记忆/工具/环境三者支撑"问题求解循环"，循环产生行动作用于环境，环境产生反馈回到循环。

- **工具是连接 Agent 和环境的接口**（search()→搜索引擎、query_db()→数据库、read_file()→文件系统、run_test()→测试环境、deploy()→生产环境）：**工具不是目的，而是 Agent 作用于环境的接口。**
- **记忆解决时间维度**：环境告诉 Agent"现在世界是什么样"，记忆告诉 Agent"过去发生过什么"。有了记忆，Agent 不会重复失败（A 失败 → 尝试 B，而非反复试 A）。**环境提供空间状态，记忆提供时间历史。**
- **缺少的东西：目标（Goal）**。必须单独拿出来，因为没有目标就不知道为什么做。"P99 是 500ms"只是状态，真正的问题是"把 P99 降到 100ms"，即 `State → Goal` 定义了问题。整个问题求解过程就是 `Current State → Problem → Goal → 理解→检索→推理→行动 → New State → Goal 达成了吗？(是→Done / 否→循环)`。
- **规划（Planning）**：一旦"行动"不是一步而是 `A→B→C→D`，就需要在"推理"和"行动"之间加入 `推理 → 规划 → 行动`。

**最终模型：**

> **目标 → 理解 → 检索 → 推理 → 规划 → 行动 → 环境反馈 → 新状态 → ……**

而**记忆贯穿整个循环，工具连接 Agent 与环境**。核心循环：理解→检索→推理→行动→观察→循环；支撑要素：记忆+工具+环境；驱动因素：目标。这已经非常接近理解现代 Agent 架构的一个核心抽象。
